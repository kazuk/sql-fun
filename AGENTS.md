# Scripts

Various utility scripts are located under `.local/bin/`.

- `check-test-flow`: Runs the standard build and test flow.
- `big-source`: Lists large source files based on their size (line count).
- `update-stats`: Updates project statistics.

# Statistics

Statistics are stored in the stats directory. During reviews, we check the impact of changes by comparing diffs in these statistics.

- coverage.txt: A coverage summary text generated by `llvm-cov`.

- Committed coverage statistics can lag behind the code they accompany because PR creation and merge order can differ. A fresh report may therefore include changes unrelated to the current PR; do not assume every difference is a regression or measurement instability.
- If a difference is concerning, inspect the relevant commit history and regenerate coverage at earlier commits (going back several commits if needed) in a separate worktree, using the same toolchain, features, and test commands. Run measurements sequentially and compare freshly generated reports to distinguish a stale baseline from a code change or measurement variability.

# Build and Test

You can build and run tests using the `check-test-flow` script.

- Run `check-test-flow` and `update-stats` sequentially, never concurrently. Their tests share temporary build directories and can interfere with each other's cleanup.

# External Tool Prerequisites

- When planning work that invokes or depends on an external tool, verify its availability in the development/CI Dockerfile (`ci/github-actions/Dockerfile`), contributor setup instructions (`CONTRIBUTING.md`), user installation documentation, and the current environment.
- Include any missing tool installation or setup documentation in the implementation plan. Clearly document required runtime tools as prerequisites for the affected CLI feature.

# Language

- English is the official language of the `sql-fun` repository. Use English when creating or updating issues, pull requests, discussions, review comments, and other repository communications, including their titles and bodies.
- Use English for commit messages, documentation, and code comments you add or modify.
- Use the user's preferred language for conversation.

# Branches

- Run `git fetch origin` before branch operations to refresh remote-tracking references. If fetching fails, resolve the failure before proceeding.
- Create new branches from `origin/<base-branch>` (for example, `origin/main`) rather than a potentially stale local base branch. This also applies when creating branches with `git worktree add`.

# Commits

- Commits must follow the Conventional Commits specification.

# Versioning and Compatibility

- This project does not yet guarantee SemVer compatibility. Packages currently published on crates.io serve primarily as name reservations.
- During this phase, breaking API changes do not require compatibility shims, deprecated aliases, or version bumps solely for SemVer compliance. Do not request those changes in reviews solely on SemVer grounds.
- Package version bumps are handled during release operations; do not include them in feature or refactoring pull requests unless explicitly requested.
- Preserve explicit compatibility checks required by a feature, such as exact codegen version matching.

# Issues

- Before creating an issue, read the templates in `.github/ISSUE_TEMPLATE/` and use the one that matches the issue: `bug_report.md` for bugs, `feature_request.md` for feature requests, or `maintenance.md` for refactoring and maintenance. If none applies, use a structure appropriate to the task rather than forcing it into an unrelated category.
- Include the selected template's sections and follow its title and label conventions. State when information is unknown or not applicable rather than inventing details.
- When updating an issue, preserve the applicable template structure and existing relevant information.

# Pull Requests

Before submitting a pull request, update statistics by running the `update-stats` script.

- Before creating or updating a pull request, read `.github/PULL_REQUEST_TEMPLATE.md` and include all of its sections in the description.
- Check only items that have actually been completed. Explain items that were not performed or are not applicable, and disclose any remaining validation gaps.

# User-Facing Documentation Planning and Review

- When planning user-facing documentation changes, identify the intended reader, the task or decision the information supports, and the appropriate document for it.
- Review documentation requirements from issues against that reader's needs during planning. If a requirement asks for implementation details without a user-facing purpose, flag the mismatch in the plan and propose keeping it in internal documentation or tests instead. Do not silently discard explicit requirements.
- Document observable behavior, usage, prerequisites, limitations, and naming rules that users must follow. Include implementation details only when they help users use the feature, make a decision, or troubleshoot a problem; internal correctness requirements do not automatically belong in the manual.
- During plan review, verify the proposed documentation scope and placement before implementation begins. For each planned addition, check whether it changes what the reader needs to know or do. Recheck this when reviewing the final documentation diff.

# Coding Guidelines and Reviews

- Before implementing or modifying Rust code, including tests, read `docs/internal-rules/rust-coding-guideline.md` and identify the rules that apply to the change.
- In particular, test placement follows a repository-specific convention. Before adding or moving tests, read and apply the "Test placement" section of that guideline.
- Before committing or requesting user review, review the diff against those rules and fix any violations. Include test code, constructors, and callers in this review. A successful build or test run does not establish guideline compliance.
- Existing code is not a justification for repeating a pattern that conflicts with the guidelines. Keep corrections within the scope of the task rather than expanding into unrelated cleanup.
- Explicit user instructions take precedence over the guidelines. Explain any necessary departure from the guidelines and its reason; do not silently treat a task-specific decision as a repository-wide rule.
- Keep Rust coding rules and their rationale in the coding guideline rather than duplicating them here. Prefer automated lint enforcement for mechanically checkable rules; manually review the design requirements that linting cannot verify.

# Lookup dependency documentation

- When consulting Rust dependency documentation, first determine the resolved crate version from Cargo.lock. If Cargo.lock is unavailable or the dependency is not locked, inspect the relevant Cargo.toml version requirement before using docs.rs.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
