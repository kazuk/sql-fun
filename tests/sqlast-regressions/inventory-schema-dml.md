# Schema-dependent DML migration

These fixtures replace the SQL-observable assertions from the PostgreSQL
resolver groups below. Both PostgreSQL 17 and 18 were checked through the
actual CLI/server and the maintained catalog installation before removing Rust
assertions. Each schema dump matches the original column types and nullability;
inputs analyze independently and never execute their writes.

## Non-equivalent controlled contexts

- Original `delete::reports_invalid_delete::parameter_conflict` remains as
  `synthetic_parameter_conflict_retains_its_diagnostic`. For
  `DELETE FROM items WHERE $1 RETURNING $1::integer`, the synthetic context
  reports a problem; the production CLI has no diagnostic on either version.
  Both development oracles accepted PREPARE of this form (against `pg_class`,
  immediately DEALLOCATEd, without executing DELETE). An explicit boolean to
  integer cast is available in the real catalog. No fixture claims to replace
  the controlled-context rejection.
- Original `update::validates_destination_rules::array_parameter` remains as
  `synthetic_array_parameters_retain_assignment_compatibility`. The small
  resolver context accepts `UPDATE arrays SET a[$1]=$2` without problems;
  production CLI reports `parameter_type_unresolved` on both versions. Do not
  substitute a fixture expecting that diagnostic for the original success
  assertion. Other destination-rule cases move to `schema-update.json`.
